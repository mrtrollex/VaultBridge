# TrueNAS Community App packaging design

**Backlog item:** VB-080

**Status:** Accepted design; packaging is not implemented

**Decision date:** 2026-09-02

This document defines how a future TrueNAS Community App should package the normal VaultBridge
image. It does not add a catalog definition, publish an image, assign a release version, or claim
catalog availability.

## Decision summary

VaultBridge remains one platform-neutral application:

```text
mrtrollex/VaultBridge
        |
        | publishes the normal release image
        v
ghcr.io/mrtrollex/vaultbridge:<released-version>
        |
        | configured by
        v
truenas/apps ix-dev/community/vaultbridge
        |
        +-- one VaultBridge container
        +-- /vault  authoritative Markdown
        +-- /data   persistent, rebuildable semantic state and caches
        +-- port 8000 -> configurable TrueNAS Web Port
        +-- Web Portal -> /ui/
```

The catalog definition is a distribution and configuration adapter. It must not build VaultBridge,
fork the runtime, add a second UI service, or move TrueNAS behavior into the API, CLI, dashboard, or
domain services.

The accepted upstream definition belongs in `truenas/apps`; the VaultBridge repository owns the
runtime, Dockerfile, GHCR image, API, CLI, bundled dashboard, and generic deployment documentation.
Temporary test fixtures are acceptable during VB-081, but a permanent second authoritative catalog
copy or a `VaultBridge-TrueNAS` runtime fork is not.

Research was performed on 2026-09-02 against `truenas/apps` master commit
[`dee192fd89095cafa0ea93c19d40dfa1ca468dc9`](https://github.com/truenas/apps/tree/dee192fd89095cafa0ea93c19d40dfa1ca468dc9).

and record any convention changes before implementation.

Authoritative source:

- the pinned upstream
  [`CONTRIBUTIONS.md`](https://github.com/truenas/apps/blob/dee192fd89095cafa0ea93c19d40dfa1ca468dc9/CONTRIBUTIONS.md),
  including its repository structure, question schema, render library, local CI, migration, security,
  storage, and submission rules;
- the current library at research time was `2.3.11`; that number is evidence, not a version to pin
  before VB-081.

Current conventions relevant to VaultBridge are:

- all new contributions target `ix-dev/community/<app>/` and the `community` train;
- source files describe metadata, static image values, questions, and a Jinja2 Compose template;
- `item.yaml`, the copied `templates/library/` tree, and rendered Compose output are generated by the
  upstream tooling rather than hand-authored;
- form values are merged with `ix_values.yaml`, rendered through the current library, and deployed as
  Docker Compose;
- app containers should run non-root, with `run_as_context` recording metadata and `set_user`
  enforcing the rendered runtime identity;
- `private: true` masks a question value in the UI, but upstream explicitly describes this as UI
  masking, not as an encrypted secret store;
- `ix_volume` is the preferred default for app-owned persistent data; existing operator data can use
  a `host_path` question;
- standard port values use `bind_mode`, `port_number`, and optional `host_ips`; an empty host-IP list
  renders wildcard IPv4 and IPv6 binds;
- Web Portals are rendered through `tpl.portals.add(...)` and support a path such as `/ui/`;
- resource questions map CPU and memory limits into the rendered Compose deployment;
- `.github/scripts/ci.py` generates metadata/library artifacts, renders test values, deploys with
  Compose unless render-only is requested, and waits for container health;
- upstream currently says there is no easy supported path for pre-submission TrueNAS UI testing.
  That limitation must be handled as an explicit VB-082 gate, not hidden by local Compose success.

## Install wizard contract

The normal install requires only an API key, an existing vault path, and acceptance or adjustment of
the default Web Port. Other fields have safe defaults. Standard labels and resource groups remain
available because they are current upstream conventions, but arbitrary extra storage and arbitrary
environment-variable inputs are intentionally omitted.

### VaultBridge Configuration

| Field | Question contract | Default | Rendered behavior |
|---|---|---|---|
| API Key | Required string, `private: true`, minimum 32 characters | Empty; user must supply | `API_KEY` |
| Previous API Key | Optional string, `private: true` | Empty | `API_KEY_PREVIOUS`; omit or pass empty when unused |
| Filesystem Watcher | Boolean | `false` | `SEMANTIC_WATCH_ENABLED` |
| Watcher Debounce Seconds | Required positive integer | `1` | `SEMANTIC_WATCH_DEBOUNCE_SECONDS`; equivalent to the upstream `1.0` default |

The API key is user-supplied. The definition must not generate an unshown key because users need the
credential for the dashboard and API clients, and the current upstream convention does not provide a
clearly superior compatible secret-generation lifecycle.

Both key fields are masked in the form and must never be placed in app notes, README examples, portal
URLs, test fixtures, screenshots, logs, or support instructions. The packaging template passes them
only as container environment values. A privileged TrueNAS or Docker administrator can necessarily
inspect deployed configuration; `private: true` must not be described as encryption or as protection
from the host administrator.

Rotation is deliberately short-lived:

1. set the new value as **API Key** and the old value as **Previous API Key**;
2. save/redeploy and migrate clients to the new key;
3. clear **Previous API Key** and save/redeploy again.

The previous key is not a fallback for a missing current key and has no automatic expiry. The form
description must say to keep the overlap brief.

The watcher remains visible because a TrueNAS vault is commonly changed outside VaultBridge by
Obsidian or synchronization software. It stays disabled by default, matching VaultBridge. Its help
text must explain that startup synchronization still reconciles downtime changes and that watcher
events depend on the host-path filesystem delivering notifications to the container.

Rate-limit controls are not exposed in the initial wizard. The normal image defaults remain active:
enabled, 120 requests per 60 seconds, and at most 1024 peer buckets. These are advanced process-local
operator settings and do not justify four more normal-install fields. A future need must be handled as
a separate packaging change with value migration as required; VB-081 must not add an unrestricted
`additional_envs` escape hatch.

### User and Group Configuration

| Field | Question contract | Default |
|---|---|---|
| User ID | Required integer, minimum `1` | `568` |
| Group ID | Required integer, minimum `1` | `568` |

The main container uses `set_user(values.run_as.user, values.run_as.group)`. UID/GID `0` is rejected;
VaultBridge must not run as root. Configurability is retained because an existing vault dataset may
already be owned by another non-root identity. Defaults follow the TrueNAS `apps` identity and the
VaultBridge image's prepared `/data` ownership.

`app.yaml` records a `run_as_context` for one container that can run as any non-root UID/GID, with
the documented default `568:568`. This metadata does not itself enforce the runtime identity; the
Compose template does.

### Network Configuration

The container always listens on bridge networking at port `8000`. The wizard exposes:

| Value | Contract | Default |
|---|---|---|
| `network.web_port.bind_mode` | Hidden/fixed to `published` | `published` |
| `network.web_port.port_number` | Required integer from 1 through 65535, labelled **Web Port** | `8765` |
| `network.web_port.host_ips` | Standard optional host-IP selector | empty list, meaning wildcard IPv4/IPv6 under the current library |
| `network.networks` | Standard optional additional Docker networks | empty list |

The template maps the selected host port to fixed container port `8000`. The existing VaultBridge
operator default `8765` is retained because it is valid under the current schema and familiar to
existing deployments. The schema validates the numeric range; TrueNAS/Docker remains responsible for
rejecting an occupied host address/port during installation. VB-082 must exercise a real collision
and confirm the error is actionable.

Host networking is not exposed: VaultBridge does not require it, it weakens isolation, and it makes
the host-port/portal contract less clear. The app requests no capabilities, devices, Docker socket,
or fixed host mounts other than the user-selected storage below.

The direct app endpoint is HTTP. TLS belongs at an operator-managed reverse proxy; the definition
must not offer a certificate selector that the current VaultBridge container cannot consume.

### Storage Configuration

#### Obsidian Vault -> `/vault`

The vault field is required and supports only an existing `host_path`. Its path uses the current
`hostpath` schema so the operator can browse/select a dataset or directory. It is read/write by
default. An explicit **Read Only** toggle may be enabled for special retrieval-only deployments, but
its help text must state that create/append operations will fail and that read/write is the supported
normal mode.

ACL handling follows the current normalized host-path form:

- **Enable ACL** defaults to `false` so installing VaultBridge never silently rewrites an existing
  vault ACL;
- when enabled, the operator deliberately grants the selected UID/GID traverse and read/write access
  through the TrueNAS ACL form;
- when disabled, the selected UID/GID must already have effective access through existing POSIX
  ownership/permissions or ACLs.

The permissions helper must **not** run against `/vault`. In particular, it must not recursively
`chown`, `chmod`, strip, or replace an existing vault ACL. Installation should fail clearly on
insufficient access rather than mutate authoritative user data. The app never creates a hidden copy
of the vault and never deletes external Markdown on upgrade, rollback, or uninstall.

#### Semantic / Derived Data -> `/data`

Derived data offers the current `ix_volume` and `host_path` choices:

- default: an app-managed ixVolume with hidden dataset name `data`, ACL disabled, mounted read/write;
- alternative: an existing operator-selected host path, with the same normalized ACL controls;
- no temporary, SMB, NFS, or arbitrary additional-storage option in the first definition.

The current permissions helper runs in `check` mode for `/data` using the selected UID/GID. For the
default ixVolume, current library behavior enables automatic permissions unless ACL handling is
selected. For a host path, ownership/ACL changes occur only when the operator explicitly selects the
corresponding current-platform permission option; otherwise access remains operator-managed.

`/data` contains the semantic SQLite/index state, FastEmbed/model cache, and Hugging Face cache. The
template fixes:

```text
VAULT_PATH=/vault
SEMANTIC_DATA_PATH=/data
HF_HOME=/data/huggingface
```

The volume persists across container restarts and normal app upgrades. It is rebuildable from
`/vault`, but it is not ephemeral. The default ixVolume follows the TrueNAS-managed app-data
lifecycle and may be removed during uninstall depending on the current uninstall choice; VB-082 must
record the exact UI behavior. The host-path alternative is externally owned and must never be
deleted by the app. `/vault` is always authoritative regardless of the `/data` choice.

### Labels Configuration

Include the current standard optional labels list, default empty, scoped only to the VaultBridge
container. It is not required for a normal install and may not be used to introduce host access or
override the application contract.

### Resources Configuration

Use the current `resources.limits` form:

| Limit | Default | Rationale |
|---|---:|---|
| CPUs | `2` | Allows indexing work without monopolizing a normal NAS. |
| Memory | `4096` MB | Matches current Community App practice and leaves headroom for the local model and initial indexing. |

These are configurable limits, not claimed minimum hardware requirements. VB-082 must validate first
model load and indexing with a representative disposable vault at the defaults. If the verified
image cannot complete that gate, the default must be raised with evidence rather than allowing a
normal installation to fail from an avoidable out-of-memory condition. No GPU fields are needed.

## Container, health, and portal contract

The future template creates one main container named `vaultbridge` from the `image` entry in
`ix_values.yaml`, plus the standard transient permissions helper only when `/data` needs it. The
helper is not another VaultBridge service and has no network access. The main container has no added
Linux capabilities and runs as the selected non-root UID/GID.

The container health check targets `http://127.0.0.1:8000/health/live`. It must use an executable
already present in the normal image. Because the current image includes Python but not curl or wget,
VB-081 should render a JSON-array custom check using Python's standard-library HTTP client; it must
not change the VaultBridge image merely to add a probe binary.

`/health/live` is intentionally the Docker/TrueNAS health check: it reports whether the API process
is serving and remains `200` while the model downloads or semantic indexing runs. `/health/ready`
remains the operator/API readiness signal and may return `503` during expected startup work or when
vault/data access is broken. `/health` remains the richer public diagnostic source used by the
dashboard Overview. Semantic readiness must not cause TrueNAS to restart a live indexing process.

The Web Portal is rendered through the current library with:

```text
name: Web UI
scheme: http
host: selected host IP or TrueNAS host
port: configured Web Port
path: /ui/
```

In template terms, it is the equivalent of
`tpl.portals.add(values.network.web_port, {"scheme": "http", "path": "/ui/"})`. It opens the
bundled same-origin dashboard in the one VaultBridge service. It does not embed the UI in a TrueNAS
frame, create a proxy, create another web service, include remote frontend assets, or place the API
key in the URL.

## Image and release contract

The only permitted runtime image repository is:

```text
ghcr.io/mrtrollex/vaultbridge
```

VB-080 does not select a release version and does not assert that a dashboard-capable release exists.
Before VB-081 can render a deployable definition, VB-075 (or its factual successor) must provide a
public, anonymously pullable, dashboard-capable release with a verified OCI digest and the required
platform.

When that dependency exists:

- `ix_values.yaml` uses the normal GHCR repository and an exact released SemVer tag, never `latest`,
  a branch tag, or a TrueNAS-specific image;
- `app.yaml.app_version` matches that upstream VaultBridge release; the catalog package's own
  `app.yaml.version` starts at the upstream-required initial package version and changes for catalog
  definition revisions independently of the VaultBridge release;
- VB-082 resolves the exact tag to its OCI digest, records it, verifies the expected source,
  revision, version, license, and platform metadata, performs an anonymous pull, and runs the tested
  content by immutable digest where the validation path permits an image override;
- the submitted catalog source follows current upstream tag conventions. Current upstream examples
  use repository plus tag rather than digest syntax, so VB-081 must not fabricate an unsupported
  digest field. Tag-to-digest identity is an evidence gate.

No `vaultbridge-truenas`, second UI image, source build, or catalog-owned runtime image is allowed.

### Supported TrueNAS versions

The design targets the current Docker Compose-based TrueNAS Apps system and current Community train;
it does not claim a minimum TrueNAS release from static research alone. The future `app.yaml` should
add `annotations.min_scale_version` only when a packaging feature requires it or VB-082 has proved a
real compatibility floor. VB-082 records the exact TrueNAS release/build tested, and the initial
support statement is limited to the earliest release that passes the complete install/edit/restart/
upgrade/uninstall gate and remains acceptable under then-current upstream policy. The existing
`README_TRUENAS.md` support statement applies to its separate source-built Custom App workflow and
must not be copied automatically into Community App metadata.

At VB-081, the source contribution is expected to be:

```text
ix-dev/community/vaultbridge/
|-- app.yaml                              required, hand-authored metadata
|-- ix_values.yaml                        required, hand-authored image/constants
|-- questions.yaml                        required, hand-authored wizard schema
|-- README.md                             required, brief hand-authored description
`-- templates/
    |-- docker-compose.yaml               required, hand-authored Jinja2 template
    `-- test_values/
        |-- basic-values.yaml             required: host-path vault, ixVolume data, watcher off
        |-- host-data-watcher-values.yaml required by this design: host-path data, watcher on, rotation placeholder
        `-- readonly-vault-values.yaml    required by this design: explicit read-only vault render
```

Current tooling also creates or copies:

```text

templates/library/base_v2_x_x/            generated copy of selected library; do not hand-edit
```

`app_migrations.yaml` and `migrations/` are optional and are not needed for the initial definition.
Add them only when a later catalog revision changes stored question values in a way that requires a
migration. Image upgrades alone do not justify a no-op migration.

The exact upstream file set and generated-artifact policy must be rechecked against current master at
VB-081 because upstream owns this structure.

## Install, edit, upgrade, rollback, and uninstall

### Fresh install

1. Select an existing vault host path and deliberately ensure the selected non-root UID/GID has the
   required access.
2. Accept the default derived-data ixVolume or select an operator-owned host path.
3. enter a new API key, optionally enable the watcher, and choose an available Web Port.
4. Install. The permission helper may prepare `/data`; it never re-owns `/vault`.
5. TrueNAS starts the normal VaultBridge image. Container health becomes healthy through
   `/health/live` without waiting for indexing.
6. Open **Web Portal**, which targets `/ui/`; unlock the dashboard with the same API key.
7. Observe `/health/ready`/Overview until vault access and semantic search are ready.

### Configuration edit

TrueNAS preserves stored values and recreates/restarts the container as required. Changing UID/GID or
storage requires the operator to grant the new identity access first. Changing the API key follows
the two-deploy rotation sequence. Changing the port updates both publishing and the portal. Turning
the watcher on or off takes effect after redeploy.

### Upgrade

An app upgrade changes the exact released image tag and `app_version`, preserves the vault mapping,
`/data`, question values, and masked key values, then recreates the same one-container application.
The VaultBridge runtime owns any semantic-index invalidation/rebuild required by its model or index
format. The catalog must not manipulate SQLite or Markdown directly.

Before offering an upgrade, verify the source release, public image, tag-to-digest mapping, OCI
metadata, release notes, configuration compatibility, fresh install, and upgrade path. The default
ixVolume and host-path `/data` alternatives must both persist across the tested upgrade.

### Rollback

Rollback is supported only between image/package versions explicitly verified in VB-082. If a newer
runtime changes derived-data compatibility, rollback may require discarding/rebuilding `/data` or
restoring an operator snapshot; it must never roll back or delete `/vault`. Do not add speculative
destructive migrations. If the current TrueNAS UI or catalog does not support a safe rollback, report
that gate as unsupported rather than claiming it.

### Uninstall

Uninstall removes the app containers and configuration according to TrueNAS behavior. The definition
contains no code that deletes storage. An external vault host path is always operator-owned and must
remain untouched. An external `/data` host path also remains. The default ixVolume follows the
operator's current TrueNAS uninstall-data choice and may be removed; that is acceptable because its
contents are derived, but the UI behavior must be captured in VB-082.

## Validation strategy

All fixtures use disposable paths, placeholder keys, and synthetic Markdown. No resolved Compose
containing secrets, private paths, user content, or complete environments may be retained or pasted
into evidence.

### VB-081 - implement and statically/render test

1. Refresh upstream master, contributor guidance, the latest non-v1 library, and the three reference
   patterns; document material drift from this design.
2. Confirm the required dashboard-capable GHCR release is public and verified. Do not choose a
   not-yet-published or floating image.
3. Implement only the file structure above in a working `truenas/apps` branch or a reproducible
   temporary fixture; do not change VaultBridge runtime code.
4. Run the upstream CI tool for every test-values file, first render-only and then its supported local
   deployment path. Inspect generated Compose without publishing secret-bearing output.
5. Assert from sanitized parsed output:
   - exactly one VaultBridge application container and only the conditional permissions helper;
   - exact image repository/tag and fixed container port `8000`;
   - required/private API fields and optional/private previous key;
   - `/vault` host-path mount, read/write default, explicit read-only variant, and no vault permission
     action;
   - persistent `/data` ixVolume and host-path variants plus permission-helper behavior;
   - non-root selected UID/GID, no capabilities, no privileged mode, no host network, and no Docker
     socket;
   - fixed path environment, watcher off/on values, and image-default rate limiting;
   - Python liveness health check against `/health/live`, not readiness;
   - host port mapping and Web Portal path `/ui/`;
   - CPU/memory limits and empty optional labels/networks.
6. Exercise invalid/missing required values, invalid UID/GID, invalid port, invalid debounce, missing
   host paths, and malformed storage choices through the current schema/render tooling.
7. Verify no fixture, note, README, rendered artifact, diff, or test output contains a real secret.

VB-081 ends with an implemented, current-schema definition and passing upstream render/local tests.
It does not claim TrueNAS UI behavior, catalog availability, or upstream acceptance.

### VB-082 - real TrueNAS lifecycle validation

Use a disposable supported TrueNAS installation, isolated ports, a synthetic vault, disposable
derived data, and the exact release digest recorded for the test. Classify every result as PASS,
FAIL, or REQUIRES LIVE/UPSTREAM VERIFICATION.

The runbook must cover:

- fresh install with the normal host-path vault and default ixVolume `/data`;
- private fields masked on entry/edit and absent from notes, portal URLs, screenshots, app logs, and
  sanitized support evidence; privileged control-plane visibility is documented, not misrepresented;
- main process UID/GID and effective read/write access to both mounts, plus a permission-denied
  negative case that does not mutate the vault ACL;
- selected host address/port, an occupied-port negative case, no host networking, and no unexpected
  published ports;
- `/health/live` container health during first model download/indexing, `/health/ready` transition,
  and richer `/health` diagnostics;
- Web Portal opening `http://<host>:<port>/ui/`, same-origin UI/API requests, CSP and security headers,
  Bearer unlock, and no second service;
- authenticated list/literal/semantic requests using synthetic content;
- restart persistence for vault and semantic data;
- watcher disabled and enabled behavior using an external synthetic Markdown edit;
- API-key rotation and final previous-key removal without exposing either key;
- edit operations for Web Port and supported storage/resource settings;
- upgrade from an explicitly supported prior image/package, preserving vault, `/data`, and secrets;
- rollback only if supported and verified, otherwise an explicit unsupported result;
- uninstall proving the external vault remains byte-for-byte untouched and recording ixVolume versus
  host-path `/data` behavior;
- anonymous GHCR pull, expected platform and OCI labels, tag-to-digest equality, and immutable-digest
  runtime evidence.

Current upstream contributor guidance says there is no easy supported pre-submission TrueNAS UI test
path. VB-082 must first check for a then-current supported preview/custom-catalog mechanism. If none
exists, use the exact rendered Compose through the supported TrueNAS custom-YAML path for runtime,
storage, permission, health, restart, upgrade, and uninstall evidence, but leave question-form,
edit-form, generated Portal metadata, and Discover-tile behavior as **REQUIRES UPSTREAM VERIFICATION**.
Local Compose or custom YAML must never be reported as proof of a catalog wizard.

### VB-083 - upstream submission and Discover availability

Only after VB-082's required gates pass should VB-083 prepare the contribution under
`ix-dev/community/vaultbridge/`. Submission does not guarantee acceptance. During development,
VaultBridge does not automatically appear in users' Discover pages. A normal Community tile becomes
available only if the upstream pull request is accepted, merged, generated into the catalog, and
distributed by TrueNAS. Documentation may then state factual Community App availability; it must not
call the app official or promise approval before merge.

## Security invariants

The package preserves, rather than replaces, VaultBridge security boundaries:

- protected routes continue to require the Bearer API key;
- the browser stores a validated key only in namespaced, tab-scoped `sessionStorage` and clears it on
  logout/`401` according to the existing dashboard contract;
- the strict UI CSP, local assets, `nosniff`, no-referrer policy, text-only dynamic rendering, and
  same-origin UI/API remain unchanged;
- the application container runs non-root with no additional capabilities, privileged access,
  Docker socket, host networking, or NAS administration access;
- neither packaging nor helper containers log keys, queries, content, headers, raw private paths, or
  resolved secret-bearing environments;
- `/vault` remains external authoritative Markdown and `/data` remains separate rebuildable state;
- no arbitrary storage destination, arbitrary environment override, vault deletion, dashboard
  editing, index mutation control, or TrueNAS-specific API is added.

## Out of scope

VB-080 does not implement or authorize runtime, API, UI, semantic ranking/model/chunking, Dockerfile,
dependency, or image changes. It does not create a TrueNAS-specific UI, NAS administration features,
dashboard editing, a second application service, a source build, a release, a tag, a GHCR
publication, an upstream contribution, or a catalog-availability claim. VB-081, VB-082, and VB-083
remain separate gated tasks.
